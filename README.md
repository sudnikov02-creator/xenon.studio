# xenon.studio

Персональная платформа фотографа: записи, клиенты, сообщения, маркетинг и аналитика — в одной спокойной
панели. Интерфейс на русском языке, светлая тема, синий акцент.

## Стек

| Слой | Технологии |
| --- | --- |
| Frontend | React 19, TypeScript, Vite 8, React Router 7, lucide-react, свои CSS-токены и компоненты |
| Backend | Node.js, Express 4, better-sqlite3 (WAL), cookie-сессии, bcryptjs |
| Realtime | Server-Sent Events (`/api/events`) — заявки, сообщения, бейджи, настройки |
| PWA | vite-plugin-pwa (Workbox), манифест, push-обработчик, офлайн-страница |
| Уведомления | web-push (VAPID), Telegram/email — в следующих этапах |

## Запуск

```bash
npm install
npm run dev        # API :3001 + Vite :5173
```

Откройте `http://localhost:5173`.

Демо-доступ (создаётся при первом запуске):

```
email:  studio@xenon.studio
пароль: xenon2026
```

Учётные данные подсказываются на экране входа. Отключить подсказку и демо-сид:

```bash
XENON_DEMO=0 XENON_SEED=0 npm run dev
```

### Другие команды

```bash
npm run typecheck   # проверка типов
npm run build       # production-сборка (dist/)
npm start           # Express отдаёт dist + API на PORT (по умолчанию 3001)
```

### Переменные окружения

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `3001` | порт API/прод-сервера |
| `XENON_DATA_DIR` | `./data` | каталог базы SQLite |
| `XENON_DB` | `data/xenon.db` | путь к файлу базы |
| `XENON_SEED` | `demo` вне production, иначе `off` | демо-данные при пустой базе: `demo` — включить, `off` — выключить |
| `XENON_DEMO` | `1` | показывать демо-доступ на экране входа |
| `XENON_VAPID_PUBLIC` / `XENON_VAPID_PRIVATE` | генерируются в БД | постоянные ключи push-уведомлений |
| `XENON_SECRET` | встроенное значение | ключ подписи cookie сессии: задайте свой на постоянном хостинге |
| `VERCEL` | — | автоматически выставляется Vercel: БД уезжает в `/tmp` |

База, сессии и VAPID-ключи создаются автоматически: схема накатывается при старте, а на пустой базе
приложение ведёт на регистрацию фотографа и само создаёт статусы записей и настройки студии. Каталог
`data/` в `.gitignore`.

Вход не зависит от таблицы `sessions`: cookie подписана HMAC и проверяется на любом инстансе, поэтому
переходы по разделам не «выкидывают» из кабинета, даже если serverless-хостинг успел пересоздать базу.
Если база пересоздана, владелец студии восстанавливается из cookie, а пароль предлагается задать заново
в профиле.

## Прогресс по этапам

- **Этап 1 — готов:** инициализация, PWA, схема БД, авторизация фотографа, каркас панели
  (сайдбар с анимированными подменю, шапка, нижняя навигация, шторка «Ещё»), уведомления и тосты,
  живые бейджи, страницы 404 и истёкшей ссылки, профиль и смена пароля.
- **Этап 2 — готов:** дашборд с метриками (записи, доход, средний чек, новые клиенты — с трендом к
  прошлому месяцу и анимацией счётчика) и виджетами «Съёмки сегодня», «Заявки», «Календарь», «Доход по
  неделям»; drag-and-drop перестановка с «призраком» виджета и пунктирным плейсхолдером, перестановка
  из меню виджета; настройка видимости и порядка метрик и виджетов, параметры каждого виджета;
  подтверждение и отклонение заявки (с комментарием клиенту) прямо с дашборда; переключение месяца в
  мини-календаре; сохранение раскладки в настройках студии; счётчик заявок в сайдбаре и нижней
  навигации; обновление по SSE.
- **Этап 3 — готов:** услуги и пакеты (создание, редактирование, дублирование, удаление с проверкой
  вхождений в пакеты, сортировка и сдвиг, доп. опции с типами и ценами, валидация полей и 422-ошибки),
  рабочее расписание (часы по дням, перерывы, выходные, буфер, минимальный запас времени, горизонт
  записи, исключения по датам), переключатели и сохранение через `PATCH /api/settings`, публичный
  список услуг для формы записи, живое обновление по SSE.
- **Этап 4 — готов:** публичная форма записи `/booking` на пять шагов (услуга или пакет → дата и
  свободное время → дополнения и пожелания → контакты → подтверждение) с полноэкранным режимом на
  телефоне, плавными переходами между шагами и живым расчётом стоимости; слоты строятся по
  расписанию с учётом перерывов, буфера, минимального запаса времени и уже занятых съёмок;
  подтверждение телефона шестизначным кодом (демо-режим показывает код на экране, SMS-провайдер —
  точка расширения `sendCode()`); та же форма используется фотографом в окне «Новая запись» без кода;
  настройки формы `/admin/settings/booking-form` (код, поля, шаг времени, вступление); новая заявка
  сразу появляется на дашборде по SSE.
- **Этап 5 — готов:** раздел «Записи» `/admin/bookings` — вкладки по статусам с живыми счётчиками,
  фильтры по периоду (сегодня/неделя/месяц/предстоящие/прошедшие) и сортировка по дате съёмки, дате
  заявки или стоимости, поиск по имени, телефону, услуге и коду с задержкой ввода, постраничная
  подгрузка «Показать ещё» (таблица на десктопе, карточки на телефоне); карточка записи открывается
  поверх списка и показывает контакты клиента, услугу или состав пакета, дополнения, пожелание
  клиента, стоимость и историю событий; смена статуса, перенос на свободный слот с проверкой
  занятости, отмена с причиной, заметки и ссылка на галерею, мягкое удаление в корзину; всё
  обновляется по SSE без перезагрузки страницы.
- **Этап 6 — готов:** клиентская страница записи `/b/:code` — личная ссылка клиента без входа в систему:
  крупная дата и время, обратный отсчёт, статус, состав услуги или пакета, стоимость с дополнениями,
  пожелание клиента, галерея, история событий и правила студии; свайп-вкладки «Детали / История /
  Помощь» со скользящим подчёркиванием и автоподстройкой высоты; перенос на свободное время прямо со
  страницы (только слоты из рабочего расписания, с учётом минимального запаса и занятости) и отмена с
  причиной; действия доступны по флагам статуса (`client_can_reschedule`, `client_can_cancel`), а для
  поздних изменений показывается подсказка позвонить фотографу; контакты фотографа (телефон, Telegram,
  Instagram, почта) настраиваются в профиле; страница обновляется по SSE-каналу записи и опросом как
  страховкой на serverless, фотограф получает уведомление о каждом действии клиента.
- **Этап 7 — готов:** настройка статусов `/admin/settings/statuses` — цепочка работы с записями с
  drag-and-drop и стрелками, отдельный блок статусов отмены (они всегда в конце), создание и
  редактирование (название, палитра из 14 цветов и свой цвет, живое превью пилюли), три флага —
  стартовый, финальный и «отменяет запись» с гарантией уникальности каждого, права клиента на перенос
  и отмену прямо в статусе (действуют на странице `/b/:code`), счётчик записей и предстоящих съёмок,
  удаление с переводом записей в выбранный статус и сохранением событий, обновление по SSE.
- **Этап 8 — готов:** CRM клиентов `/admin/clients` — единая база с сегментами (все, VIP, с записью,
  новые, спящие, без съёмок, чёрный список) и живыми счётчиками, поиск по имени, телефону (в том числе
  по цифрам), почте и мессенджерам, сортировка по визиту, дате добавления, сумме, числу съёмок и имени,
  подгрузка «Показать ещё»; карточка клиента открывается в overlay: метрики (съёмки, потрачено, средний
  чек, ближайший визит), контакты со ссылками tel/mail/t.me, VIP и чёрный список переключателями, заметка
  с сохранением, история съёмок с ценами и статусами; создание и правка в overlay, удаление с
  подтверждением (запрещено при наличии записей), обновление списка по SSE.
- **Первый запуск:** база SQLite создаётся автоматически, демо-данные — только при `XENON_SEED=demo`
  (или вне production); на пустой базе вход ведёт на регистрацию, после неё создаются статусы записей и
  настройки студии.
- **Этап 9 — готов:** сообщения `/admin/messages` — диалоги с клиентами в одном окне (Telegram, почта),
  фильтры «все / непрочитанные / ждут ответа» и поиск по имени, телефону и тексту, счётчики
  непрочитанных, лента чата с разделителями дней, системными сообщениями и записями клиента,
  отправка сообщений с выбором канала и быстрыми ответами, панель клиента с контактами и переходом
  в карточку, живое обновление по SSE; вкладка «Уведомления» — полная лента с фильтрами по типу и
  статусу прочтения и кнопкой «Прочитать все».
- **Этап 10 — готов:** маркетинг и движок цен — скидки `/admin/marketing/discounts` (процент или
  фиксированная сумма, период действия, привязка к услугам и пакетам, минимальный чек, авто-применение,
  живое переключение и метрики экономии), промокоды `/admin/marketing/coupons` (генерация кода,
  лимит использований, срок, фильтры и поиск), сертификаты `/admin/marketing/certificates` (номинал или
  конкретная услуга, получатель, срок, остаток, история списаний, переворот карточки, блокировка);
  сквозной расчёт цены на форме записи — авто-скидка выбирается автоматически, промокод или сертификат
  применяется к остатку, итог с зачёркнутой ценой и суммой экономии, проверка кода без перезагрузки;
  в записи сохраняются базовая цена, скидка и код, панель показывает их в карточке, всё обновляется по SSE.
- Этапы 11–16 — далее по плану (бонусы и рефералы, автоматизация и шаблоны,
  календарь/аналитика/журнал, отзывы и лендинг, повторная запись и SEO, финал).

## API дашборда

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/dashboard` | метрики месяца, заявки в ожидании, съёмки сегодня, ближайшая съёмка, мини-календарь, доход по неделям |
| `GET` | `/api/dashboard/calendar?month=YYYY-MM` | счётчики и список съёмок другого месяца |
| `POST` | `/api/bookings/:id/accept` | подтвердить заявку (переводит в статус «Подтверждена», пишет событие, рассылает SSE) |
| `POST` | `/api/bookings/:id/decline` | отклонить заявку с комментарием клиенту (до 600 символов) |

## API записи

| Метод | Путь | Назначение |

| `GET` | `/api/public/booking/options` | услуги, пакеты, правила расписания, настройки формы, условия |
| `GET` | `/api/public/booking/availability?month=&serviceId=` | свободные дни месяца с количеством слотов |
| `GET` | `/api/public/booking/slots?date=&serviceId=` | свободное время конкретного дня |
| `POST` | `/api/public/booking/verify/start` | отправить код подтверждения на телефон |

| `POST` | `/api/public/booking/quote` | расчёт цены: авто-скидка, промокод или сертификат, итог и сумма экономии |

| `POST` | `/api/bookings` | ручная запись фотографа (без кода, вне запаса времени) |

## API маркетинга

Все методы требуют авторизации и рассылают SSE-событие `marketing`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/marketing/overview` | сводка: активные скидки, экономия клиентам, промокоды, сертификаты в обороте |
| `GET` | `/api/marketing/discounts` | скидки с условиями, использованием и статусом |
| `POST` | `/api/marketing/discounts` | создать скидку (`name`, `kind` `percent\|fixed`, `value`, `items`, `minTotal`, `startsAt`, `endsAt`) |
| `PATCH` | `/api/marketing/discounts/:id` | правка или включение/выключение скидки |

## Деплой на Vercel

Репозиторий готов к деплою без ручных настроек: `vercel.json` задаёт сборку Vite, статику из `dist`
и единственную serverless-функцию `api/index.js`, которая отдаёт весь Express-API.

Прод: **https://xenonstudio.vercel.app**

Маршрутизация API: `vercel.json` переписывает `/api/*` на `/api/index`, исходный путь при этом
сохраняется, поэтому Express видит привычные адреса (`/api/auth/login`, `/api/bookings/12/accept`).
Каталог `api/[...path].js` (catch-all из файловой системы) для этого не подходит — Vercel подхватывает
такой файл только для одного сегмента пути.

```bash
# локальная проверка serverless-сборки
npm run build && npx vercel dev
```

Что важно знать про запуск на Vercel:

- **База переезжает в `/tmp`.** В serverless-окружении `server/db.js` использует `/tmp/xenon-data`,
  поэтому демо-данные создаются заново после холодного старта. Для реальной работы нужна внешняя
  БД (Postgres/Neon) — это отдельный шаг.
- **SSE работает в пределах жизни функции.** Стрим живёт до `maxDuration` (60 с), затем браузер
  переподключается; на Vercel это демо-режим, на обычном Node-хостинге ограничения нет.
- **Push-уведомления** требуют постоянного VAPID-ключа — задайте `XENON_VAPID_PUBLIC`/`XENON_VAPID_PRIVATE`
  в переменных проекта, иначе ключи генерируются на каждый старт.
- **Сессии живут в той же БД.** При нескольких параллельных инстансах функции вход может «теряться» —
  для демо это терпимо, для реальной работы нужна внешняя БД.
- **Превью-деплои** закрыты Vercel Authentication (проект включает защиту превью), прод открыт всем.
- Полноценный вариант (SQLite-файл, долгие SSE-соединения, фоновые задачи) — обычный Node-хостинг:
  `npm run build && npm start` за nginx.

## Заметки по архитектуре

- **Единственный пользователь.** Регистрация доступна только пока в базе нет аккаунта; клиенты
  взаимодействуют по индивидуальным ссылкам `/b/:code` и не имеют учётных записей.
- **Настройки студии** хранятся одной JSON-строкой и мгновенно применяются на клиенте: акцентный цвет,
  название, favicon, тема браузера. Изменения рассылаются по SSE.
- **Сессии** — httpOnly-cookie на 30 дней; пароль хранится bcrypt-хешем; вход ограничен rate-limit.
- **Realtime** — единый SSE-канал с heartbeat; бейджи непрочитанного обновляются автоматически.
- **PWA** — установка, push-handler, офлайн-страница; в dev service worker отключён, проверяйте на
  `npm run build && npm start`.
- **Раскладка дашборда** — объект в настройках: `{ metrics: Record<key, boolean>, widgets: [{ id,
  visible, config }] }`; порядок виджетов и их параметры сохраняются сразу, без кнопки «Сохранить».
- **Слоты** считаются на сервере и перепроверяются внутри транзакции при создании записи — двойная
  запись на одно время невозможна; цена тоже считается на сервере, клиентские значения игнорируются.
- **Код подтверждения** — таблица `phone_verifications`: 6 цифр, 10 минут, 5 попыток, повтор через
  60 секунд, одноразовый токен на 40 минут. В демо-режиме (`XENON_DEMO=1`) код возвращается в ответе
  и виден на экране; для реальных SMS достаточно заменить `sendCode()` в `server/lib/verification.js`.
- **Расписание** — единственный источник правды для слотов: `week[day] = { enabled, start, end,
  breaks[] }`, `exceptions[]` по датам, `bufferMin`, `noticeHours`, `horizonDays`. Перед сохранением
  расписание нормализуется и валидируется на сервере (невалидное — `422 invalid_schedule`).
